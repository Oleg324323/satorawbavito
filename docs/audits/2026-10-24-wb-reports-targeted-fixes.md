## 4. P&L: себестоимость и даты

Подтверждены и исправлены следующие дефекты:

- Legacy-мост рассчитывал подтверждённую себестоимость только после успешной проверки налога. Отсутствие налоговой настройки ошибочно скрывало уже известную себестоимость. Теперь эти результаты независимы, но прибыль всё ещё блокируется при неизвестном налоге.
- Финансовые строки без товарного движения могли требовать привязку/датированную себестоимость. Для таких строк COGS равен подтверждённому нулю. Продажа и возврат в разные дни с нулевым итогом не освобождены от проверки истории. Отсутствующий дневной разрез ненулевых gross-операций не считается нулём.
- Общая формулировка смешивала отсутствие привязки товара, примерную стоимость, недатированное свидетельство и несходящиеся дневные количества. Причины разделены. Для legacy P&L добавлены причины по строкам и даты операций, покрытие которых требует проверки; для canonical сохранены его blocker IDs.

Изменение стоимости/привязки инвалидирует только зависимые расчётные кэши. Проверен пересчёт из БД после исправления стоимости без загрузки WB. Подтверждённые стоимости не перезаписываются, даты не выдумываются, примерная стоимость не становится фактической.

**Реальный остающийся блокер этой локальной базы:** в `marketplace_accounts`, `catalog_skus`, `catalog_cost_versions` нет записей. Число в legacy-настройке/интерфейсе не является существующей записью фактической себестоимости с привязкой и действием на даты операций. В новой сборке число строк, требующих COGS, сократилось с 800 до 517: сервисные строки больше не создают ложный запрос себестоимости. Для 1025784485 за 12–18 октября COGS и налог остаются неизвестными; прибыль не объявлена подтверждённой. Для их заполнения нужны реальные связи каталога/сохранённая история и налоговая настройка, а не повторная выгрузка финансов WB.

## 7. Предыдущий период: диагноз и готовое точечное решение

Этот пункт — диагностика и предложение, **не внедрение новой очереди или широкая переделка сравнения**.

Подтверждённые причины:

1. В `repricer_tasks.refresh_report_sources_for_org.publish_preview` параметр `include_previous` зависит от `period_phase`. Во время selected-фазы он false. Далее `wb_week_sources.attach`/`wb_week_finance.attach` подставляют пустые предыдущие источники. Даже завершённая финансовая выгрузка 5–11 октября в БД в таком preview не читается; её отсутствие в UI не доказывает отсутствие первичных записей.
2. План ждёт текущие воронку/финансы и прочие источники, включая статистику/рекламу, прежде чем перейти к предыдущим окнам. Во время проверки реклама обработала 100 из 716 кампаний; локальный worker работает с concurrency=1. Другие холодные отчёты остались в очереди за этой задачей.
3. После смены экрана read-demand завершается; job штатно получает paused с сообщением «При открытии раздела сбор продолжится с недостающих данных». Это не потеря финансовых записей. Проверка нескольких экранов не должна называться завершённой сверкой всех cold-периодов.
4. Воронка имеет отдельную проблему полноты: receipt selected был sourceComplete=true, но отдельные product/field coverage остались неполными; load_funnel возвращал funnelComplete=false и needsCollection=false. Получен полный ответ поставщика, но не доказано наличие всех требуемых полей/товаров. Это не основание бесконечно повторять тот же запрос или присваивать нули.

Рекомендуемое минимальное изменение:

- Разделить **чтение сохранённого previous** и **приоритет его загрузки**. Материализовать preview с доступными предыдущими данными из БД уже в selected-фазе; сбор previous оставить после selected. Эти builder-ы не получают WB-токен, следовательно само чтение не должно запускать WB-запросы.
- Readiness и delta проверять отдельно для каждой метрики/двух источников. Полные previous-финансы должны давать сравнение выкупов независимо от отсутствующей рекламы или полей воронки; прибыль при недостающей себестоимости остаётся неизвестной.
- Обновлять `period_phase` перед принудительной публикацией preview на границе фаз. Сохранённый preview не должен навсегда оставаться с comparison-pending, если предыдущие записи уже пригодны.
- При полном receipt с неполными полями показывать терминальную причину источника с конкретными nmId/полями. Не снимать receipt и не зацикливать дозагрузку без новых свидетельств.
- Проверить resume/paused, дедупликацию одной задачи, публикацию из кэша и справедливость обслуживания cold-отчётов в рамках существующей очереди; не повышать параллелизм WB вслепую и не обходить лимиты.

Приёмочные регрессии для этого изменения: previous-finance уже в БД + selected-ads задержан → финансовое сравнение доступно без WB-вызова; previous-funnel отсутствует → только его метрики неизвестны; selected виден до previous; смена дат игнорирует старый ответ; после pause/resume пропущенные страницы не скачиваются повторно. Эта дополнительная правка сравнения в текущий diff не включена, согласно границе пункта 7.

**Последующее реальное наблюдение:** после перехода существующей задачи к previous-фазе финансовые сравнения появились без переделки очереди. Для 1025784485 API вернул 34 против 52 шт., −34,6%, 47 885,31 против 67 896,25 ₽. Поиск этого nmId на фронтенде показал 34 шт. / ↓ −34,6%; заказы 169 / ↑ +6,3%, корзины 776 / ↑ +0,4%. Комиссия и логистика имеют предыдущие суммы. Отдельная нераспределённая реклама показывает 175 554 ₽ / пред. 134 923 ₽. Прибыль/маржа и неизвестные расходы не стали подтверждёнными автоматически. Это подтверждает фазовую задержку, но не устраняет описанный дефект раннего preview и не доказывает полноту всех метрик.
